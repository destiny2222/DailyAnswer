# Backend In-App Purchase (IAP) Integration Guide

Since the backend is hosted outside this repository, this document specifies the required API endpoints, verification flow (StoreKit 2 JWS JWT verification), and database models to support the iOS premium subscription.

---

## 1. Database Model Schema

Create or update a subscription database model (e.g., `user_subscriptions` table) containing at least:

| Column Name | Type | Description |
| :--- | :--- | :--- |
| `id` | UUID / Int | Primary Key |
| `user_id` | Foreign Key | Owner of the subscription |
| `platform` | VARCHAR | `'ios'` (or `'android'`) |
| `product_id` | VARCHAR | `'com.thedailyanswer.monthly'` |
| `original_transaction_id` | VARCHAR | Unique ID of the original purchase (linking renewals/restores) |
| `latest_transaction_id` | VARCHAR | ID of the most recent renewal transaction |
| `status` | VARCHAR | Current state: `'active'`, `'expired'`, `'billing_retry'`, `'grace_period'`, `'revoked'`, `'refunded'`, `'unknown'` |
| `purchase_date` | TIMESTAMP | When the subscription was purchased |
| `expiration_date` | TIMESTAMP | When the current billing cycle expires |
| `environment` | VARCHAR | `'Sandbox'` or `'Production'` |
| `auto_renew` | BOOLEAN | Whether auto-renewal is currently enabled |
| `last_verification_date` | TIMESTAMP | Last time the receipt was checked / updated |
| `created_at` | TIMESTAMP | Record creation date |
| `updated_at` | TIMESTAMP | Record last modification date |

## 2. API Endpoints Specification

### A. POST /iap/apple/verify
Used by the iOS application when a transaction is completed or restored.

- **Authentication**: Requires a valid Bearer Token (`access_token`).
- **Input Validation**:
  ```json
  {
    "transactionId": "string (Required)",
    "originalTransactionId": "string (Required)",
    "productId": "string (Required)",
    "purchaseToken": "string (Required, JWS transaction string from StoreKit 2)"
  }
  ```

#### Verification Flow (Server-Side)
1. **Decode JWS (JSON Web Signature)**: The `purchaseToken` is a signed JWT (JSON Web Signature) payload generated by Apple (StoreKit 2).
2. **Verify Signature**: Verify the JWS signature using Apple Root Certificates (available from Apple Public Key infrastructure).
3. **Confirm Details**:
   - Verify `bundleId` matches `com.thedailyanswer`.
   - Verify `productId` matches `com.thedailyanswer.monthly`.
   - Extract `environment` (`Sandbox` or `Production`).
   - Extract dates: `purchaseDate` and `expirationDate`.
   - Check if `revocationDate` is present (if yes, subscription is refunded/revoked).
4. **Idempotent Storage & Access Grant**:
   - Check if `original_transaction_id` already exists.
   - Update subscription record status, `latest_transaction_id`, `expiration_date`, `auto_renew`, and `last_verification_date`.
   - Update `users.has_paid` flag in the user profile table to `true` (or `false` if expired/revoked).
5. **Response**:
   ```json
   {
     "success": true,
     "data": {
       "status": "active",
       "expirationDate": "2026-08-27T21:42:00Z"
     }
   }
   ```

---

### B. GET /subscription/status (or Profile lookup)
Returns user entitlement status.

- **Authentication**: Requires a valid Bearer Token.
- **Response**:
  ```json
  {
    "success": true,
    "data": {
      "has_paid": true,
      "payment_status": "active",
      "payment_expires_at": "2026-08-27T21:42:00Z"
    }
  }
  ```

---

### C. POST /webhooks/apple/app-store
Receives real-time status updates from the Apple App Store Server (App Store Server Notifications V2).

- **Payload**: Receives `signedPayload` (signed JWT).
- **Verification Flow**:
  1. Decode and verify the root `signedPayload` with Apple certificates.
  2. Extract `notificationType` (e.g., `SUBSCRIBED`, `DID_RENEW`, `EXPIRED`, `REFUND`, `REVOCATION`).
  3. Extract `data.signedTransactionInfo` (and optionally `data.signedRenewalInfo`) and decode them.
  4. Match the transaction to a user via the `originalTransactionId` (lookup table).
  5. Update the user subscription status and `has_paid` flag accordingly.
  6. Return `HTTP 200 OK` immediately.
  7. Log failures safely (avoid logging customer details or API keys).
